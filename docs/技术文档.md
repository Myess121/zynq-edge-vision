# 基于 Zynq-7020 软硬件协同的实时边缘目标检测系统 —— 技术文档（草稿）

> 标注"未上板实测"的数据为设计完成但未在板上测量的项目。

## 1. 背景与痛点

安防巡检、智慧零售、工业质检等场景需要在摄像头端就地完成目标检测：

- **云端推理延迟高、带宽成本大**：视频上传需要稳定的网络，往返延迟通常上百毫秒，且有隐私风险。
- **通用嵌入式 CPU 算力不足**：单纯依靠 ARM 核运行图像预处理和神经网络推理，帧率很低。
- **GPU 方案功耗与成本高**：难以部署在大量边缘节点。

Zynq-7000 SoC 在一颗芯片内集成双核 ARM Cortex-A9（PS）与 FPGA 逻辑（PL）。本作品将图像采集、缓存、预处理、显示等**数据密集且规则的运算放在 PL**，将推理调度、后处理和交互放在 PS，在低功耗下实现实时目标检测。

## 2. 系统总体架构

```
            ┌──────────────────────────── PL (FPGA) ─────────────────────────────┐
 OV5640 ──► │ SCCB 硬件配置 ─┐                                                    │
 (DVP)      │ cmos_capture ─► 颜色转换/像素打包 ─► VDMA(S2MM) ─┐                   │
            │                                                  │   HP0            │
            │ HDMI(rgb2dvi) ◄─ VTC ◄─ AXIS→Video ◄─ VDMA(MM2S) ┤ ◄────► DDR3 1GB  │
            │                                                  │   HP1            │
            │ AXI DMA ─► resize_accel (HLS) ─► AXI DMA ────────┘                   │
            └──────────────▲─────────────────────────────────────────────────────┘
                           │ AXI GP0（控制寄存器）
            ┌──────────────┴──────────── PS (ARM A9 x2, Linux/PYNQ 2.7) ──────────┐
            │ Python 应用：取帧 → (PL resize | cv2.resize) → YOLO-Fastest(cv2.dnn) │
            │ → NMS 后处理 → 画框/FPS 叠加 → 写回 HDMI 帧缓冲                     │
            └─────────────────────────────────────────────────────────────────────┘
```

**PS/PL 分工**

| 模块 | 位置 | 说明 |
|---|---|---|
| OV5640 上电配置（SCCB） | PL | 移植正点原子 Verilog 状态机，上电自动写约 250 个寄存器，不依赖软件驱动 |
| 图像采集 cmos_capture | PL | DVP 8bit → RGB565 → RGB888 |
| 帧缓存 VDMA | PL + DDR | 摄像头写入、HDMI 读出，三帧缓冲 |
| 预处理 resize_accel | PL（HLS） | 双线性缩放到网络输入尺寸，AXI DMA 经 HP1 搬运 |
| 推理 YOLO-Fastest | PS | OpenCV DNN，单线程/多线程 |
| 后处理 NMS、绘制 | PS | OpenCV |
| HDMI 显示 | PL | VTC + rgb2dvi，1280×720@60 |

## 3. 硬件设计（PL）

### 3.1 开发平台

- 正点原子领航者 ZYNQ-7020（XC7Z020-CLG400-2），DDR3 1GB
- OV5640 500 万像素摄像头模组（DVP 接口），配置为 640×480 RGB565 输出
- HDMI（经 HDMI-DVI 转接）显示器
- 工具：Vivado / Vitis 2026.1（由正点原子 2020.2 工程迁移升级）

### 3.2 摄像头配置与采集

原厂 PYNQ 方案通过 PS 端 AXI IIC + Python 驱动配置 OV5640。实测发现 OV5640 在软复位和 PLL 切换时会长时间拉伸 SCL，原 `XIic_Send` 实现存在死等与总线挂死问题。最终方案将配置下沉到 PL：

- `ov5640_hw_cfg.v`：封装 `i2c_ov5640_rgb565_cfg` + `i2c_dri`，SCCB 250 kHz，上电延时 20 ms 后自动配置；
- 分辨率参数化（`CMOS_H/CMOS_V/TOTAL_H/TOTAL_V`），与 VDMA 帧尺寸一致（640×480，HTS=1856，VTS=984）；
- 释放了一个 AXI IIC 外设和 PS 端驱动代码，摄像头上电即出图。

### 3.3 视频缓存与显示

- AXI VDMA 双通道：S2MM 写入摄像头帧，MM2S 读出到 HDMI；
- VTC 产生 1280×720@60 时序，axi_dynclk 产生像素时钟，rgb2dvi 完成 TMDS 编码；
- 摄像头 640×480 画面居中贴入 720p 输出帧，检测框和性能信息直接叠加在帧缓冲上。

### 3.4 HLS 预处理加速 IP

- `resize_accel`：AXI-Stream 24bit RGB 输入/输出，AXI-Lite 寄存器（src_rows/src_cols/dst_rows/dst_cols），双线性插值，最大宽度 3840；
- AXI DMA（简单模式，32bit）经 `axis_dwidth_converter`（4B↔3B）对接；DMA 主口接 HP1，与 VDMA 的 HP0 分开，避免抢占显示带宽；
- 中断接入 `concat_interrupts` → AXI INTC。

## 4. 软件设计（PS）

- 系统：PYNQ 2.7（Ubuntu 20.04，Linux 5.4，Python 3.8，OpenCV 4.2.0）
- 应用 `sw/edge_detect.py`：
  1. 加载 overlay（`.bit` + `.hwh`），通过 PYNQ 的 VideoIn/VideoOut 驱动 VDMA；
  2. `readframe()` 取帧 → 预处理（`--pl` 走 PL resize，`--cpu` 走 `cv2.resize`）；
  3. `cv2.dnn` 运行 YOLO-Fastest，NMS 后处理；
  4. 绘制检测框与 FPS/各阶段耗时，写回 HDMI 帧缓冲；
  5. 各阶段耗时写入日志，用于 PS/PL 对比。

## 5. 模型选型与部署

| 模型 | 参数量 | 计算量 | 说明 |
|---|---|---|---|
| YOLO-Fastest v1.1 (COCO) | ~0.35 M | ~0.25 BFLOPs @320 | 极轻量，适合 Cortex-A9 |

部署：输入 320×320 / 224×224 两档可切换。
部署：PYNQ 2.7 自带 OpenCV 4.2.0，其 Darknet 导入器有两个问题：不支持 `[dropout]` 层；分组（depthwise）卷积权重按稠密卷积读取，导致之后所有权重错位、输出 NaN。我们做了两种处理：

1. `model/make_cv42_model.py`：dropout 替换为恒等 maxpool，分组卷积展开为块对角稠密卷积。结果正确，但计算量暴增，320 输入需要 5.2 s/帧。
2. `model/darknet2onnx.py`（最终方案）：不依赖任何第三方库，手写 protobuf 编码，直接输出 ONNX。BN 折叠进卷积，保留分组卷积，YOLO 头的解码放到 Python 端完成。在 PC 上与原 Darknet 模型的检测结果逐框一致；在板上 320 输入降到 609.5 ms/帧，比方案 1 快 8.5 倍。

| 测试项 | 结果 |
|---|---|
| PC 静态图推理（cv2.dnn，i9 笔记本，320×320） | 约 10 ms/帧 |
| 板上静态图推理 320×320（PS，OpenCV 4.2，ONNX） | 609.5 ms/帧（约 1.6 FPS） |
| 板上静态图推理 224×224（PS，OpenCV 4.2，ONNX） | 307.9 ms/帧（约 3.2 FPS） |
| 预处理 cv2.resize（768×576→320×320，PS） | 约 7.3 ms |
| 预处理 PL resize_accel（edge_v2） | 未上板实测（设计已完成综合实现，资源与时序达标） |
| 实时演示 --cpu（edge_v1，256×256，检测在独立进程） | 显示 25–30 FPS；检测约 1.3 次/秒，推理约 0.65 s；采集卡死时自动重载硬件，约 2 s 恢复 |
| 端到端帧率 --pl | 未上板实测（依赖 edge_v2） |
| 摄像头→HDMI 直通（edge_v1，PL 配置 OV5640） | 约 25–26 FPS，连续 5400+ 帧稳定 |

**板上推理基准**（PS 端 Cortex-A9 双核 667 MHz，OpenCV 4.2.0，ONNX 模型，dog.jpg，15 帧取中位数）

| 输入尺寸 | 1 线程推理 | 2 线程推理 | 2 线程 FPS（预处理+推理） | 预处理 cv2.resize |
|---|---|---|---|---|
| 224×224 | 543.8 ms | 308.9 ms | 3.16 | 7.4 ms |
| 256×256 | 715.2 ms | 394.8 ms | 2.47 | 9.5 ms |
| 320×320 | 1096.2 ms | 606.5 ms | 1.63 | 7.2–13.8 ms |

`cv2.setNumThreads(2)` 用上两个 A9 核后，推理速度提升 1.76–1.81 倍。实时模式默认 256×256，在检测精度和速度之间折中。显示和检测解耦：PL 的 VDMA 保持摄像头到 HDMI 实时直通，检测线程异步取最新一帧推理，屏幕上同时显示"显示 FPS"和"检测 FPS/延迟"两组数字。

### 6.1 调试中解决的关键问题

| 问题 | 现象 | 原因 | 解决 |
|---|---|---|---|
| 软件 I2C 配置 OV5640 卡死 | 初始化中途卡住、花屏 | OV5640 软复位/切 PLL 时长时间拉伸 SCL，原厂 `XIic_Send` 死等，被打断后总线挂死 | 摄像头配置下沉到 PL 状态机（`ov5640_hw_cfg.v`），上电自动完成 |
| 偶发画面冻结 | 运行一段时间后停在最后一帧 | 个别行数据不完整，VDMA S2MM 报 EOL Early 错误后停止；像素时钟缺少时序约束 | 软件看门狗 1 s 无帧自动重启采集；edge_v3 补充 `cam_pclk` 时钟与输入延迟约束 |
| 识别到物体后画面卡死 | 移动摄像头对准物体时采集中断，单独复位 VDMA 无法恢复 | 摄像头排线受力导致接触不良，DVP 总线瞬时中断，S2MM 与 HLS 像素处理 IP 卡死（已由用户确认） | 检测放入独立进程（spawn）；3 s 无帧就重新加载 bitstream 并重新配置摄像头，排线恢复前每 2 s 重试一次，实测约 2 s 自动恢复；无法恢复时断电重启（开机自启服务自动拉起演示） |
| 显示偏色 | 蓝色显示成橙色 | 采集帧为 BGR，HDMI 按 RGB 输出 | HDMI 输出设为 PIXEL_BGR，由 PL color_convert 交换通道，不占 CPU；模型输入保持 RGB |
| 系统随机崩溃 | 换程序后 Python 段错误、全屏雪花 | 进程退出时没有停止 VDMA，DMA 继续写入已释放、被内核复用的内存 | 所有视频程序捕获 SIGTERM/SIGINT，退出前先关 VDMA 再释放缓冲；另提供 `stop_vdma.py` 紧急停止 |
| OpenCV 4.2 无法加载模型 | `dropout` 不支持、输出 NaN | 旧版 Darknet 导入器缺层且分组卷积权重错位 | 自研零依赖 Darknet→ONNX 转换器 |

## 7. 创新点

1. **软硬件协同划分**：采集、缓存、缩放、显示全部在 PL 流水线完成，PS 专注推理与决策；
2. **摄像头配置硬件化**：用 PL 状态机替代 PS 软件 I2C 驱动，解决了 OV5640 时钟拉伸导致的总线挂死问题，上电即出图，提升系统鲁棒性；
3. **HLS 预处理加速**：用 HLS IP + 独立 HP 口 DMA 实现预处理卸载，并提供 `--pl/--cpu` 一键对比；
4. **工具链迁移**：完成正点原子 Vivado 2020.2 工程到 2026.1 的升级、裁剪与时序收敛。

## 8. 总结与展望

本作品在低成本 Zynq-7020 平台上实现了"摄像头采集—PL 预处理—PS 推理—HDMI 显示"的完整边缘目标检测链路。后续可将卷积计算进一步用 HLS/DPU 加速，或引入量化模型提升帧率。
